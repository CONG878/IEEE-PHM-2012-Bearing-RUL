# 코드 구조화 원칙

## 1. 목적

본 문서는 프로젝트의 유틸리티 모듈을 비롯한 코드 구조를 지속적으로 유지·확장하기 위한 **코드 구조화(Code Structuring) 원칙**을 정의한다.

여기서 코드 구조화란 기존 코드의 기능을 변경하거나 불필요한 코드를 제거하는 작업이 아니라, **구성 요소를 개념적 책임에 따라 분류하고 배치하며, 섹션의 계층과 시각적 구조를 정돈하는 작업**을 의미한다.

따라서 구조화 과정에서는 기능, 알고리즘, API, 함수 시그니처, 호출 관계 및 데이터 처리의 의미를 변경하지 않는다.

---

## 2. 기본 원칙

### 2.1 기능과 구조의 분리

코드 구조화는 기능 변경과 독립적으로 수행한다.

다음 요소는 구조화의 대상이 아니며, 구조화 과정에서 변경하지 않는다.

* 함수의 동작과 알고리즘
* 함수 시그니처와 공개 API
* 데이터 처리 방식
* 함수 간 호출 관계
* 입력 및 출력의 의미
* 모델 및 평가 로직
* 기존 기능의 동작 결과

구조화의 대상은 다음과 같다.

* 함수와 클래스 등의 배치
* 상수 및 설정의 배치
* 코드의 개념적 분류
* 섹션 및 하위 섹션의 구성
* 섹션 명칭
* 주석과 구분선의 형식
* 수직 여백과 시각적 계층

---

### 2.2 개념적 책임에 따른 분류

구성 요소는 단순히 함수의 형태나 구현 방식이 아니라 **무엇을 책임지는가**를 기준으로 분류한다.

예를 들어 계산 함수라는 이유만으로 하나의 분류에 모으기보다는, 해당 계산이 어느 개념적 책임에 속하는지를 우선한다.

또한 프로젝트의 실제 단계나 워크플로가 명확한 독립적 책임을 갖는 경우 이를 구조적 경계로 활용할 수 있다.

---

### 2.3 모듈별 구조의 독립성

모든 모듈에 동일한 구조를 강제하지 않는다.

모듈마다 담당하는 책임과 복잡도가 다르므로, 각 모듈에 적합한 깊이와 구성을 사용한다.

따라서 어떤 모듈에서는 대분류만으로 충분할 수 있으며, 다른 모듈에서는 중분류와 소분류까지 필요할 수 있다.

**구조의 일관성보다 각 모듈의 개념적 명확성을 우선한다.**

---

## 3. 섹션 계층

섹션은 필요한 만큼만 사용하며, 시각적 계층이 개념적 계층을 나타내도록 한다.

### 3.1 대분류

모듈의 주요 책임 또는 독립적인 큰 영역을 구분한다.

```python
# =============================================================================
# 1. Main Category
# =============================================================================
```

`=` 구분선은 모듈의 가장 큰 개념적 경계를 나타낸다.

---

### 3.2 중분류

대분류 내부에서 독립적인 책임, 추상화 또는 워크플로를 구분할 필요가 있을 때 사용한다.

```python
# -------------------------------------------------------------------------
# Subcategory
# -------------------------------------------------------------------------
```

단순한 매개변수 차이나 함수의 변형만으로는 중분류를 만들지 않는다.

---

### 3.3 소분류

독립적인 책임이라고 보기에는 작지만, 하나의 함수 또는 작은 함수 그룹을 가볍게 구분할 필요가 있을 때 사용한다.

```python
# ----- Small Category -----
```

모든 영역에 소분류를 강제로 추가하지 않는다.

---

## 4. 세로 여백

세로 여백은 단순한 서식이 아니라 섹션의 계층을 표현하는 수단으로 사용한다.

### 대분류

대분류 헤더는 앞뒤의 충분한 여백으로 독립된 영역임을 표현한다.

```python


# =============================================================================
# Section
# =============================================================================

...
```

즉, **대분류 위에는 2개의 빈 줄, 헤더 아래에는 1개의 빈 줄**을 둔다.

### 중분류

중분류는 그 자체로 강한 구분선이므로 헤더 뒤에 별도의 빈 줄을 두지 않는다.

```python
...
# -------------------------------------------------------------------------
# Subsection
# -------------------------------------------------------------------------
def function(...):
```

### 소분류

소분류는 최소한의 여백만 사용한다. 장식적인 빈 줄을 추가하여 계층을 과도하게 강조하지 않는다.

동일한 분류에 속한 함수 사이에도 불필요한 빈 줄을 반복하지 않는다.

---

## 5. 공개 요소와 내부 구현

공개 API와 내부 구현의 개념적 역할을 구분한다.

공개 함수는 사용자가 모듈의 책임을 파악할 때 쉽게 발견할 수 있도록 배치하는 것을 우선한다.

반면 이름 앞에 `_`가 붙은 내부 함수는 구현 세부사항이므로 일반적으로 모듈 하단에 모아 둔다.

다만 이 원칙 때문에 기존의 명확한 논리적 흐름을 깨서는 안 된다. **개념적 흐름과 책임 구조가 우선한다.**

내부 구현의 세부적인 구조가 공개 API의 대분류를 결정해서는 안 된다.

---

## 6. 새로운 코드 추가 시의 분류

새로운 구성 요소를 추가할 때는 가능한 경우 즉시 기존 구조에 편입한다.

### 6.1 분류가 명확한 경우

상수, 설정, 클래스 선언 등 소속이 명확한 요소는 추가 시점에 바로 적절한 분류에 배치한다.

함수 역시 기존 분류와의 관계가 명확하다면 해당 분류에 즉시 추가한다.

### 6.2 분류가 불명확한 경우

새 함수의 책임이 아직 명확하지 않아 기존 분류 중 어느 곳에 배치할지 판단하기 어려운 경우에는 임시로 **`미분류`** 대분류를 사용한다.

```python
# =============================================================================
# N. 미분류
# =============================================================================

def new_function(...):
    ...
```

`미분류`는 정식 책임 영역이 아니다.

이는 새 함수가 가장 가까워 보이는 기존 분류, 특히 **마지막 분류에 임의로 섞이는 것을 방지하기 위한 임시 대기 영역**이다.

현실적으로 새 함수를 추가할 때마다 충분한 구조적 판단을 내리기 어려울 수 있으므로, 분류를 억지로 확정하는 것보다 임시 보류를 허용한다.

---

## 7. `미분류`의 사후 처리

`미분류`에 배치된 구성 요소는 이후 코드 구조를 재검토할 때 다시 분류한다.

다음 순서로 판단한다.

1. 기존 대분류에 편입할 수 있는가?
2. 기존 대분류 내부의 중분류로 구분할 필요가 있는가?
3. 기존 구조로 설명하기 어려운 독립적인 책임 영역이 충분히 형성되었는가?
4. 필요한 경우에만 새로운 정식 대분류를 만든다.

새로운 함수 하나가 기존 분류에 잘 들어가지 않는다는 이유만으로 즉시 새로운 대분류를 만들지 않는다.

반대로 여러 구성 요소에서 공통된 독립 책임이 확인된다면 이를 새로운 정식 분류로 승격할 수 있다.

최종적으로 `미분류`는 가능한 한 비워 두며, 장기간 정식 분류처럼 방치하지 않는다.

---

## 8. 새로운 분류를 만드는 기준

새로운 분류는 **독립적인 책임, 추상화 또는 워크플로가 존재할 때** 만든다.

다음과 같은 이유만으로는 새로운 분류를 만들지 않는다.

* 함수의 매개변수가 다르다.
* 동일한 API의 다른 옵션이다.
* 가중/비가중과 같은 동작 변형이다.
* 산술 평균/조화 평균과 같은 매개변수 기반 변형이다.
* 단순히 함수가 하나뿐이다.
* 기존 분류의 마지막에 배치하기 어색하다는 이유만 있다.

즉, **함수의 차이가 아니라 개념적 책임의 차이**가 새로운 분류의 근거가 되어야 한다.

---

## 9. 기존 구조의 보존

구조화 과정에서 기존 배치가 이미 개념적 책임을 적절하게 반영하고 있다면 이를 유지한다.

모든 모듈을 동일한 형태로 재배치하거나, 규칙의 형식적 일관성을 위해 불필요한 섹션을 추가하지 않는다.

따라서 구조화의 결과가 다음과 같을 수도 있다.

* 함수의 위치가 변경된다.
* 함수의 위치가 전혀 변경되지 않는다.
* 섹션 명칭만 변경된다.
* 구분선과 수직 여백만 변경된다.

이 모든 경우가 동일하게 유효하다.

**변경의 양이 구조화의 품질을 의미하지 않는다.**

---

## 10. 구조화의 핵심 원칙

전체 원칙은 다음과 같이 요약할 수 있다.

> **명확한 책임은 즉시 분류하고, 불명확한 책임은 ****`미분류`****에 임시 보류하며, 정기적인 구조 검토를 통해 필요한 경우에만 기존 분류에 편입하거나 새로운 분류를 만든다.**

그리고 더 근본적인 원칙은 다음과 같다.

> **모든 코드를 규칙에 맞추는 것이 목적이 아니라, 코드의 개념적 구조가 필요한 만큼 명확하게 드러나도록 하는 것이 목적이다.**

따라서 코드 구조화에서는 **일관성보다 책임의 명확성**, **형식적 대칭성보다 실제 구조**, **과도한 사전 분류보다 필요에 따른 점진적 분류**를 우선한다.
